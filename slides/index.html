Part I · Pretraining

I

What is a repeated token worth?

Chai and Xiong · The scaling geometry of multi-epoch pretraining · arXiv 2610.05591

The question

Public text grows more slowly than compute

So pretraining increasingly repeats data, and every run faces three questions.

  1. How many epochs should a run take over the data it has?
  2. How should that number change with model size?
  3. Does anything besides the epoch count matter: order, allocation, source?

Method

Price a repeated token twice

Each run of \(R\) epochs over \(U\) unique tokens, \(D = RU\) in total, is compared with two one-epoch runs of the same model.

Value · data-matched baseline: one epoch on U

\[ \eta = \frac{U_{\mathrm{eq}} - U}{D - U} \]

\(U_{\mathrm{eq}}\) is the fresh budget that reaches the same loss. \(\eta = 1\) if repeats were as good as fresh data, 0 if worthless.

Cost · compute-matched baseline: one epoch on D

\[ \Delta L = L(N, U, R) - L(N, D, 1) \]

The extra held-out loss, in bits per byte, paid for repeating instead of collecting new data at the same compute.

Evidence · 1B unique CommonCrawl tokens

Small models keep gaining; large ones reverse after four epochs

Second epoch

0.87–1.02

fresh tokens per repeated token, at every budget in the main grid.

Best epoch count

15.3 → 3.6

Quadratic minima from 127M to 2B parameters, with the corpus held fixed.

Fitted laws

One variable prices the cost of repetition

Cost of repetition Eq. 3 · §4.2

\[ \Delta L = 0.0203\, z^{1.07}, \quad z = \frac{(R-1)\,N_{\mathrm{total}}}{U} \]

Extra epochs per unique token per parameter. Fitted to 113 of 140 repeated runs, \(R^2 = 0.96\); no size term once embeddings are counted.

Critical epochs Eq. 4 · §4.3

\[ R_c \approx 2.7 \left(\frac{D}{N}\right)^{0.24} \]

Where a repeat is worth half a fresh token: 4.0–5.3 epochs up to 20 tokens per parameter, about ten at 300. 8% RMS over 35 crossings.

Fitted on CommonCrawl, GPT-2 BPE, 23M–361M non-embedding parameters, 5–300 tokens per parameter, 2–16 epochs.

Takeaways

What to do with a fixed corpus

  1. Transfer epoch counts with data, not size. When unique data grow with the model, the best epoch count barely moves.
  2. Larger budgets tolerate more repetition. Half value after four to five epochs at 20 tokens per parameter, about ten at 300.
  3. Grow model and epochs together, in roughly equal shares, up to the critical epoch count.
  4. Spread and shuffle repeats. Replaying shards back to back costs +0.46 bpb at 511M and 16 epochs.

Tokenization falling short

TKEval · 7 probes × 200 items

Models read subwords, not characters

So we ask what they know about the letters inside their own tokens, and the substrings shared across them.

0 → 81%

Across projects

Three habits that carry over

  1. Price data by its value, not by how often it was seen.
  2. Score the whole trajectory, and report reliability (pass^k) next to coverage (pass@k).
  3. Hold the task fixed and vary one factor, so a drop measures that factor and nothing else.
