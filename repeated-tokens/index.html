What is a repeated token worth?

The scaling geometry of multi-epoch pretraining

Yekun Chai, Haoyi Xiong

arXiv preprint 2610.05591

Paper PDF

Overview

As pretraining increasingly repeats data, every run faces three questions: how many epochs to take, how that number should change with model size, and whether anything besides the epoch count matters.

We price a repeated token against two references: one epoch on the same data, which gives its value, and fresh data at equal compute, which gives its cost. A grid over model size, training tokens per parameter and epochs gives every repeated run both baselines.

Findings

One variable
z = (R−1)N/U
Excess loss over fresh data at equal compute follows a power law in extra epochs times parameters over unique tokens. No further size term is needed.
Second epoch
0.87–1.02
Value of a second epoch relative to a fresh token, at every training budget per parameter on the grid.
Size trend
15 → 4 epochs
Loss-minimizing epoch count at fixed unique data, from 127M to 2B parameters. When unique data grow with the model, it barely moves.
Order matters
+0.46 bpb
At identical counts, replaying shards consecutively raises loss by up to 0.46 bits per byte.

In practice

  • Transfer epoch counts with data, not size.To reuse an epoch count on a larger model, scale the unique data with it.
  • Stop near the critical epoch count.With unique data fixed, the compute-optimal run grows model size and epochs together until loss stops improving, near the point where a repeat is worth half a fresh token.
  • Spread and shuffle repeats.Concentrating repeats on fewer samples raises loss, lower-entropy sources such as code degrade faster, and re-tokenizing repeats helps only under heavy repetition.

Setup

Models
Decoder-only Transformers, 14M to 2B parameters
Optimizer
Muon for hidden matrices, Adam elsewhere; learning rate annealed to each run’s horizon
Data
SlimPajama, seven sources, GPT-2 byte-level BPE
Metric
Bits per byte on held-out test sets of each source
